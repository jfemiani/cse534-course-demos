Every idea so far in this module has been about the model reaching out mid-conversation: deciding to call a tool, deciding to keep looping. This lesson is about something that happens before any of that: text prepared ahead of time, for the model to read rather than to act on immediately, saved to a file and loaded only when it is relevant. AI coding assistants such as GitHub Copilot, Claude Code, and Codex have converged on a shared pattern for this over the last couple of years, built around two kinds of files.

Instructions the model reads, not tools it calls

AGENTS.md holds project-wide instructions for whatever repository it lives in: how that project is organized, which commands build it, which conventions its code follows. This course's own demo repository has one, telling an assistant working in it how the Canvas pages, demos, and slides are organized. It is loaded every time the assistant works in that project, the same way a human contributor might read a repository's CONTRIBUTING.md before their first pull request.

SKILL.md holds instructions for one specific capability rather than a whole project: how to accomplish one kind of task well, including the mistakes an assistant is likely to make without the extra guidance. A skill file carries a short name and description up front. The assistant reads only that short description for every skill it knows about, and loads the full instructions for a skill only once it decides that skill matches the current task.

Both files exist to fill a slot a model call already has. The Responses API takes a top-level instructions string, kept separate from the conversation's input, and the OpenAI Agents SDK exposes the same idea one level up: building an Agent(...) means setting its own instructions= string, exactly what lesson 4.3's 02a_agent_loop_agents_sdk.py does with instructions="Answer questions about instructors using the lookup tools.". AGENTS.md and SKILL.md do not add a new mechanism to the API. They change how a coding assistant assembles the text that goes into that same field before it ever calls the model: concatenating AGENTS.md, plus whichever SKILL.md files matched the current task, into one instructions string. GitHub Copilot, Claude Code, and Codex are all filling the same parameter this way; only the file names for where the text comes from differ.

Nothing here is a result that gets proven. It is an engineering convention that spread because writing detailed guidance once, in a file, is cheaper than retyping the same instructions string in every conversation, and it is barely a couple of years old. Two things suggest it will persist: it is plain text with almost no format to get wrong, and GitHub Copilot, Claude Code, and Codex converged on nearly the same file layout independently, which usually means multiple teams landed on the same answer rather than one company setting a fashion the others copied. Two things suggest it might not: as context windows grow and models get better at inferring conventions directly from a codebase, writing anything down may matter less, and as coding assistants mature, today's plain markdown files could get folded into stricter, product-specific configuration. Treat the underlying idea, instructions loaded on demand instead of retyped every time, as durable; treat the exact file names as a snapshot of 2024-2026 practice.

Skills are how non-programmers "program" a model

Writing a good SKILL.md does not require writing code. It requires writing down, precisely, the steps a capable person would take and the mistakes a careless one would make: the same thing a training manual or a checklist does for a new hire. A support lead who has never opened a terminal can still author a skill for "how we redact a customer PDF" or "how we phrase a refund email," and an assistant that reads it will follow those steps as reliably as it follows a Python function's docstring. For a large and growing set of tasks, prose instructions in a file now shape what a model does, alongside code, without anyone writing a line of that code. The line to draw is not "smaller than a function"; it is closer to management than to engineering.

Because a SKILL.md is just a text file with a small, agreed-upon header, it can be shared the way a script or a library can. Anthropic publishes a public repository of skills at github.com/anthropics/skills: working examples for tasks like filling out a PDF form, editing a spreadsheet, or following a company's brand guidelines, each one a folder with a SKILL.md and whatever helper scripts it needs. The format is not tied to one vendor. Sites such as agentskills.io index skills that work across Claude, JetBrains' Junie, Gemini CLI, and other assistants, the way a package index serves more than one language runtime, so an assistant can be pointed at a skill someone else already debugged instead of having every team write its own from scratch. The same thing exists one level up. A growing number of repositories publish reusable agents, not just skills: a bundle of instructions plus a specific set of tools and a name, ready to be invoked as a subagent rather than authored from nothing. This course's own repository does the same thing at a small scale: real skills and agents built for maintaining these Canvas pages, kept outside the public demo folder because I don't want to show exactly how the sausage is made. This lesson swaps in generic stand-ins instead (adding a TL;DR, adding hashtags, flagging unsourced claims). They follow the same convention and behave the same way; only the subject matter changed.

Subagents: a third way to manage context

Several coding assistants add a third piece alongside AGENTS.md and SKILL.md: a way to dispatch a whole separate copy of the assistant to handle one bounded piece of work, then report back. Claude Code calls this a subagent, configured in a .claude/agents/*.md file with its own name, its own system prompt, and its own restricted list of tools; its Task tool is what spawns one. GitHub Copilot, the assistant I used to help author these pages, has the same capability under a different name: a task tool that launches background agents such as explore, code-review, or rubber-duck, each with its own tool access and its own model. This course's own custom instructions add project-specific subagents on top of that list, educational-reviewer for checking a lesson's clarity, canvas-page-editor for revising a Canvas page. A subagent runs in its own context window: it can read many files and take many steps, and only its final answer comes back into the conversation that dispatched it.

That is the context-management idea a skill cannot provide on its own. A skill adds instructions to whatever context is already running; it does not get a context of its own. A subagent does, so handing off a task that would otherwise take twenty exploratory steps keeps those twenty steps out of the parent conversation's transcript entirely.

There is a code-level version of this same idea, for a different situation: building a multi-agent application rather than working inside a coding assistant. The OpenAI Agents SDK has agent.as_tool(); Google's Agent Development Kit has something similar. Both let one agent call another as a tool. That connects to this course's earlier lessons on the agent loop, but it solves a different problem: you are building the application, not talking to an assistant that already exists. See the Claude Code subagents documentation for the coding-assistant version.

The three sort out cleanly once the question is when does each one load, and for what. AGENTS.md is the "who": it loads once per project and stays in context for every task, so it is the right place for ground rules, project layout, and conventions that should not change from one task to the next. SKILL.md is the "how": it loads only when a specific task calls for it, so it is the right place for the steps of one procedure, adding hashtags to a post, phrasing a TL;DR, and nothing that needs to apply outside that task. A subagent is neither; it is a separate copy of the assistant, dispatched when a step needs its own context window, or a different and more restricted set of tools, than the parent conversation already has, such as a reviewer limited to read-only tools.

That still leaves a real gray area. A "code reviewer" could be a SKILL.md, a checklist any assistant reads before commenting on a diff, or a subagent, a dedicated reviewer dispatched to look at a diff with its own read-only tools and its own context. Both are defensible; the choice trades off simplicity against isolation, not correctness against error.

The demo

The three example skills below, adding a TL;DR, adding hashtags, and flagging unsourced claims, are generic writing tasks, similar in spirit to the skills in public skill repositories, rather than this course's own production skills.

The demonstration program below ties those three skills to a real model call. Given a single request, it decides which skill applies, loads that skill's instructions into a small agent built just to follow them, and hands that agent to a second, manager agent as a tool it can choose to call. The full source is linked first; the sections that matter are pulled out afterward, each with a note on what goes in and what comes out.

05_agent_instructions.py (full source on GitHub)

read_skill takes the path to one SKILL.md file and returns two things: a dictionary of its front-matter fields (just name and description) and the body text underneath, kept separate so the body can stay unread until something needs it. Called on add_hashtags.SKILL.md, it returns a dictionary like {"name": "add_hashtags", "description": "Use when a post needs hashtags..."} alongside the five numbered steps that follow the front matter.

keyword_score takes two plain strings, a task description and a skill's description, and returns an integer: how many words they have in common. It stands in for the model's own judgement about which skill fits a task. Scored against "a caption for this hike photo I want to post on instagram," add_hashtags' description ("Use when a post needs hashtags for a social platform...") shares words like "post" and scores higher than a description about summarizing long text.

This block takes the one task string and the list of (frontmatter, body) pairs read_skill produced for every file in sample_skills/, and prints one line per skill: its name and its keyword_score against the task. Nothing has been loaded in full yet; only the short descriptions were compared, the same order a real assistant's dispatch step follows.

This line takes the same list of skills and picks the single (frontmatter, body) pair with the highest score, discarding the rest. For the Instagram-caption task that pair is add_hashtags; its full body, the five-step procedure, is now in hand for the first time in the program. Every other skill's body is never read at all.

This block builds an Agent named after the winning skill, whose instructions= string is a short generic preamble with the skill's own body appended underneath. The result is an agent whose only job is to follow those five hashtag steps; nothing else about it changed. Handed a different task, this same code would build a differently instructed agent instead.

This block wraps that specialist with the Agents SDK's as_tool(), which takes an agent plus a name and description and returns something a different agent can call like any other tool. A second Agent, the manager, is built with that wrapped specialist as its only tool. The manager never reads the skill's instructions; it only sees a tool called writing_specialist, described by the skill's own front-matter description, and decides for itself whether to call it.

This is the one line in the file that makes a real model call: it takes the manager agent and the original task string, and returns a result object whose final_output is printed below it. Everything before this line only set the call up; nothing was sent to a model until here.
