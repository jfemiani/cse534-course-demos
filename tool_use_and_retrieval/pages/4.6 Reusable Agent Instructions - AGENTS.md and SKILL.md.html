Instructions the model reads, not tools it calls

Every idea so far in this module has been about the model calling code. This lesson is about the opposite direction: code (or a person) writing instructions for the model to read, saved to a file, loaded only when they are relevant. AI coding assistants such as GitHub Copilot, Claude Code, and Codex have converged on a shared pattern for this over the last couple of years, built around two kinds of files.

AGENTS.md holds project-wide instructions: how this particular repository is organized, which commands build it, which conventions its code follows. It is loaded every time the assistant works in that project, the same way a human contributor might read a repository's CONTRIBUTING.md before their first pull request.

SKILL.md holds instructions for one specific capability rather than a whole project: how to accomplish one kind of task well, including the mistakes an assistant is likely to make without the extra guidance. A skill file carries a short name and description up front. The assistant reads only that short description for every skill it knows about, and loads the full instructions for a skill only once it decides that skill matches the current task.

This is an engineering convention, not a theorem

Nothing here is a result that gets proven. It is a convention that spread because it worked: writing detailed guidance once, in a file, is cheaper than re-explaining the same thing to an assistant in every conversation. Treat it the same way you would treat a team's coding style guide.

The demo

This repository uses SKILL.md files the same way, as a live example rather than just a demo. The demo below is a small, simplified stand-in for that dispatch step: given a task description, it scores two example skill files by how many words their short description shares with the task, and reports which one it would load in full. A skill's description and a document chunk are different kinds of text, but the same keyword-matching idea from the previous lesson applies to both. Real assistants make this decision with the model's own judgement, not a fixed word-overlap score; the scoring here is a stand-in to make the idea visible.
