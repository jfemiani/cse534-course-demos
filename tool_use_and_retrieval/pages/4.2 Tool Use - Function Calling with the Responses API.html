Ask a language model how many times the letter "r" appears in "strawberry" and it will often get the answer wrong. The model does not read a word one letter at a time. It breaks text into tokens, the same units from the entropy and n-gram lessons, and a token can span several letters at once, so counting individual letters inside one is a strange task for it. Splitting the check off to a small Python function fixes this: the function counts correctly every time, and the model only has to know when to ask for it.

That handoff is what "tool use" or "function calling" means. The model does not run any code itself. It emits a structured request naming a function and its arguments. Your code runs the real function and sends the result back. The model then uses that result to write its answer.

Demo 6 in Module 2 used structured output: the model's final answer had to fit a schema you defined. Tool use is a different moment in the conversation. The model is not shaping its final answer here; it is asking for information it does not have, before it writes that answer at all.

Note the direction of each arrow: the model never touches the tool directly. It only sends a request to the code you control, and your code decides whether and how to run the tool.

Three ways to define a tool

All three variants below ask the same letter-counting question and call the same count_letter tool. Each one sets tool_choice="required" (or the Agents SDK equivalent) to force the model to call the tool every time, purely so the walkthrough is reliable and easy to read. This is a teaching shortcut, not something to copy into production code: normally the model decides for itself whether a tool is needed, which means your code must check the response before assuming a function call is present. A response might come back as ordinary text instead, and code that skips that check will crash the first time the model decides it does not need the tool.

Before running any of the three demos below, install this module's dependencies once: pip install -r requirements-tool-use-and-retrieval.txt (see requirements-tool-use-and-retrieval.txt).

1a: hand-typed JSON schema

The tool's schema is a plain Python dict, and the arguments the model sends back are parsed with json.loads(). This is the bare-metal version: nothing hides how the API's tool format actually looks on the wire.

01a_function_calling_json.py (full source on GitHub)

This is the real function behind the tool: ordinary Python, nothing special about it yet.

The tool's schema, typed by hand: this dict is the whole reason the model can ask for this tool at all. It never sees count_letter's Python source, only this description. name is what the model will echo back when it wants to call the tool. description is the only hint the model gets about when to use it, so vague wording here produces a model that calls the tool at the wrong times or not at all. parameters is a JSON Schema object, the same schema language used in demo 6's structured output, here describing the tool's input instead of the model's final output. required tells the model both fields must be present, not optional.

Here is the request, and reading the model's function call out of the response. response.output is a list of items the model produced; in general it can hold ordinary text, one function call, or several. response.output[0] is safe to index here only because tool_choice="required" plus a single available tool guarantees the model returns exactly one item, and that item is a function call. Production code without those two guarantees must loop over response.output and check each item's type before assuming a function call is present. call.arguments comes back as a JSON-formatted string, not a Python object, which is why json.loads() runs before the arguments are used.

Sending the real function's result back: count_letter(**args) is the only line in the whole file that actually runs code. Everything before it is the model asking, not answering. The second client.responses.create(...) call sends that result back tagged as function_call_output, with the same call_id the model used to ask, so it knows which request this result answers.

Output:

Model asked to call: count_letter({'word': 'strawberry', 'letter': 'r'})
Real function returned: 3
Assistant: The letter “r” appears 3 times in “strawberry.”

1b: schema generated from a Pydantic model

Demo 6 defined its output schema as a Pydantic model. This variant defines a tool's arguments the same way: one small Pydantic class, with the JSON schema the API needs read straight off it via model_json_schema(). The model's arguments come back validated through model_validate_json() instead of merely parsed. Reading the schema off a class beats hand-typing the same fields twice, once in the function's signature and once in a JSON dictionary.

01b_function_calling_pydantic.py (full source on GitHub)

The Pydantic model that defines the tool's arguments: CountLetterArgs declares each argument once, as a typed field, instead of as a hand-typed JSON Schema entry.

The real function behind the tool is ordinary Python, same as 1a.

The schema is read off the model instead of typed by hand. CountLetterArgs.model_json_schema() produces the same parameters dict 1a typed by hand; the field names, types, and required list all come from the class above instead of being written twice.

Here is the request, and validating the model's arguments. CountLetterArgs.model_validate_json(call.arguments) replaces 1a's json.loads(). This does not just parse the string; it checks the types against the model, so a malformed response raises a clear validation error instead of silently passing bad data to count_letter.

Sending the real function's result back is unchanged from 1a. Only how the schema and the arguments are produced has changed, not the round trip itself.

Output:

Model asked to call: count_letter(word='strawberry' letter='r')
Real function returned: 3
Assistant: The letter “r” appears 3 times in “strawberry.”

1c: schema generated by the OpenAI Agents SDK's @function_tool

1a and 1b each produced a schema, then hand-wrote the same call/response round trip. The OpenAI Agents SDK offers a third way to produce that schema: decorate a plain function with @function_tool and it reads the name, description, and JSON schema straight off the function's type hints and docstring, no schema class needed. This demo keeps the same manual round trip as 1a and 1b, to isolate that one change: how the schema itself gets produced.

The pattern across 1a, 1b, and 1c: the same schema gets easier to produce as the tooling around it matures, hand-typed, then read off a Pydantic model, then read straight off a function signature. The next lesson builds on this further, automating the round trip itself, not just the schema.

01c_function_calling_agents_sdk.py (full source on GitHub)

The real function behind the tool is ordinary Python, same as 1a and 1b.

Wrapping the function generates its schema: function_tool(count_letter) reads the name, description, and JSON schema straight off the function above and exposes them as .name, .description, and .params_json_schema, the same three pieces 1a typed by hand and 1b read off a Pydantic model, generated here from a type-hinted signature and docstring instead.

The schema is assembled from the wrapped function's attributes: the tools list is built from count_letter_tool.name/.description/.params_json_schema, then handed to client.responses.create(...) exactly as in 1a and 1b.

The request is unchanged from 1a and 1b: nothing about the round trip itself changes here, only the schema's origin changed above.

Sending the real function's result back: count_letter(**args) calls the original plain function directly. The function_tool-wrapped object is not itself callable; it exists to generate the schema, not to run the function.

Model asked to call: count_letter({'word': 'strawberry', 'letter': 'r'})
Real function returned: 3
Assistant: The letter “r” appears 3 times in “strawberry.”
