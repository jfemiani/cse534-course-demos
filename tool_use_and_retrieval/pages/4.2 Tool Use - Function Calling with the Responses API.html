Ask a language model how many times the letter "r" appears in "strawberry" and it will often get the answer wrong. The model does not read a word one letter at a time. It breaks text into tokens, the same units from the entropy and n-gram lessons, and a token can span several letters at once, so counting individual letters inside one is a strange task for it. Splitting the check off to a small Python function fixes this: the function counts correctly every time, and the model only has to know when to ask for it.

That handoff is what "tool use" or "function calling" means. The model does not run any code itself. It emits a structured request naming a function and its arguments. Your code runs the real function and sends the result back. The model then uses that result to write its answer.

Demo 6 in Module 2 used structured output: the model's final answer had to fit a schema you defined. Tool use is a different moment in the conversation. The model is not shaping its final answer here; it is asking for information it does not have, before it writes that answer at all.

Note the direction of each arrow: the model never touches the tool directly. It only sends a request to the code you control, and your code decides whether and how to run the tool.

Three ways to define a tool

All three variants below ask the same letter-counting question and call the same count_letter tool. Each one sets tool_choice="required" (or the Agents SDK equivalent) to force the model to call the tool every time, purely so the walkthrough is reliable and easy to read. This is a teaching shortcut, not something to copy into production code: normally the model decides for itself whether a tool is needed, which means your code must check the response before assuming a function call is present. A response might come back as ordinary text instead, and code that skips that check will crash the first time the model decides it does not need the tool.

1a: hand-typed JSON schema

The tool's schema is a plain Python dict, and the arguments the model sends back are parsed with json.loads(). This is the bare-metal version: nothing hides how the API's tool format actually looks on the wire.

What to look for:

  • The tools list is a plain dict: name, description, and a JSON Schema parameters object, typed by hand.
  • response.output is a list of items the model produced — in general it can hold ordinary text, one function call, or several. response.output[0] is safe to index here only because tool_choice="required" plus a single available tool guarantees the model returns exactly one item, and that item is a function call. Production code without those two guarantees should loop over response.output and check each item's type before assuming it is a function call.
  • call.arguments comes back as a JSON-formatted string, not a Python object, which is why json.loads() runs before the arguments are used.
  • count_letter(**args) is the only line in the whole file that actually runs code — everything before it is the model asking, not answering.
  • The second client.responses.create(...) call sends the result back via function_call_output, tagged with the same call_id, so the model knows which request this result answers.

Output:

Model asked to call: count_letter({'word': 'strawberry', 'letter': 'r'})
Real function returned: 3
Assistant: The letter “r” appears 3 times in “strawberry.”

1b: schema generated from a Pydantic model

Demo 6 defined its output schema as a Pydantic model. This variant defines a tool's arguments the same way: one small Pydantic class, with the JSON schema the API needs read straight off it via model_json_schema(). The model's arguments come back validated through model_validate_json() instead of merely parsed. Reading the schema off a class beats hand-typing the same fields twice, once in the function's signature and once in a JSON dictionary.

What to look for:

  • CountLetterArgs is a Pydantic model declared once; CountLetterArgs.model_json_schema() produces the same parameters dict that 1a typed by hand.
  • CountLetterArgs.model_validate_json(call.arguments) replaces 1a's json.loads(). This does not just parse the string, it checks the types match the model, so a malformed response raises a clear validation error instead of silently passing bad data to count_letter.
  • The rest of the round trip — the response.output[0] indexing, the function_call_output reply — is unchanged from 1a. Only how the schema and the arguments are produced has changed.

Real function returned: 3

1c: schema generated by the OpenAI Agents SDK's @function_tool

1a and 1b each produced a schema, then hand-wrote the same call/response round trip. The OpenAI Agents SDK offers a third way to produce that schema: decorate a plain function with @function_tool and it reads the name, description, and JSON schema straight off the function's type hints and docstring, no schema class needed. This demo keeps the same manual round trip as 1a and 1b on purpose, to show that @function_tool only replaces the schema step. It does not require an Agent or a Runner to work, and this demo deliberately does not use them.

The Agents SDK's Agent and Runner classes are real, and useful, but they automate something this lesson has not covered yet: a dispatch loop that keeps calling tools on its own until it has enough information to answer. That is the subject of the next lesson, the agent loop. Introducing them here, for a single tool call, would hide the very round trip this lesson exists to show.

What to look for:

  • count_letter is a plain function, same as 1a. function_tool(count_letter) wraps it and exposes .name, .description, and .params_json_schema — the schema, generated, not typed.
  • The tools list is built from those three attributes, then handed to client.responses.create(...) exactly as in 1a and 1b. Nothing else about the round trip changes.
  • count_letter(**args) calls the original plain function directly. The function_tool-wrapped object is not itself callable; it exists to generate the schema, not to run the function.

The pattern across 1a, 1b, and 1c: the same schema gets easier to produce as the tooling around it matures — hand-typed, then read off a Pydantic model, then read straight off a function signature. The next lesson, the agent loop, continues that pattern one step further: once Agent and Runner are introduced there, the entire round trip shown in this lesson — call the API, notice the function call, run the real function, send the result back — is handled automatically.
