Suppose you want an agent that can answer "When can I meet Professor Femiani in person this week?" To answer that, the agent needs two separate facts: his office hours, and his room number. The model has no way to know either one from training. It was not trained on this week's schedule, and it cannot look up a room number on its own, so it has to reach for tools for both.

What is new is that one tool is not enough here. The model has to call one tool, read what it returns, decide it still does not have everything it needs, call a second tool, and only then write an answer. It has to keep going through that call-observe-decide cycle for as many steps as the question needs, not just one.

This repeated cycle has a name in two different communities. OpenAI's documentation calls it the agent loop. The research paper that first described it calls it ReAct, short for Reason and Act (Yao et al., 2022). Both names describe the same thing.

The demo: let the Agents SDK run the loop

Writing that loop by hand is not hard for two tools, but it is the same handful of steps every time: check what the model asked for, run the matching function, send the result back, repeat. The OpenAI Agents SDK packages up exactly that pattern, so you describe the pieces once and let the SDK drive the loop.

The word "agent" gets used loosely in the field to mean almost anything that calls tools on its own. The SDK gives it a precise, narrower meaning, split across two objects with different jobs:

An Agent is not a loop, and it does not run anything by itself. It is a configuration: which model to call, its instructions (the system-prompt-style text telling it how to behave), and the list of tools it is allowed to use. Creating one makes no API call at all; it is closer to a job description than a running process.

A Runner is what actually executes a conversation with an Agent. Given an Agent and a question, it is the piece that calls the model, checks whether the response is a final answer or a request to call a tool, runs that tool if so, sends the result back, and repeats. The loop itself, the whole call-observe-decide cycle, lives in the Runner: it is the one making every model call, not just the one running tools.

The previous lesson's demo showed you how the process works, but in the future you will want to use the SDK's Agent and Runner instead of writing the loop by hand. This is clearer, and less error-prone.

This demo gives the model two tools, lookup_office_hours and lookup_room_number, and asks the two-part question above. Each tool is a plain Python function decorated with @function_tool from the Agents SDK; handing both tools to an Agent and calling Runner.run_sync(...) (the synchronous entry point; the SDK also has an async version, but this keeps the demo free of async/await) runs the entire call-observe-decide cycle in one line. This is the version to default to: for any task past a single tool call, the Agents SDK is doing real work for you, not just saving typing.

Mixing your own tools with hosted tools

An Agent's tools=[...] list is not limited to functions you wrote. For example, OpenAI provides WebSearchTool(), which wraps one of OpenAI's built-in tools: it is hosted (cloud-run), meaning OpenAI runs the search itself, so no code on your side executes for that call. Handing the SDK a list with both kinds, [lookup_room_number, WebSearchTool()], changes nothing about the loop: Runner.run_sync(...) still calls whichever tool the model asks for, local or hosted, and keeps going until the model has an answer.

WebSearchTool is one of several tools the Agents SDK provides ready-made:

  • WebSearchTool: lets the agent search the web
  • FileSearchTool: This will be covered up-next in the chunking-and-retrieval lesson
  • CodeInterpreterTool: lets the model run code in a sandboxed environment
  • ImageGenerationTool: generates images from a prompt- we already used this to generate images in the first module!
  • HostedMCPTool: exposes a remote MCP server's tools to the model

Each one works the same way in the tools=[...] list: no code on your side runs for the call, since OpenAI hosts and executes it. That is the whole distinction between these and a plain @function_tool-decorated Python function, which always runs on your side.

This demo asks one question that needs both: a room number from the local tool and a real news story from the hosted one, so the two kinds of tool call show up side by side in the same run.

MCP: hosting your own tools the way OpenAI hosts theirs

The WebSearchTool and CodeInterpreterTool are each fixed tools that OpenAI hosts on its own servers. This is an example of an externally hosted tool. Sometimes you do not want to build a whole agent yourself; you just want to provide tools that other people's agents can use. The Model Context Protocol, or MCP, is how you do that. MCP uses remote procedure calls to invoke functions hosted on an external server: the server lists the tools it provides, and it can respond to a call by executing one of them, running it on the external provider's machine and sending the result back. This is appealing because it lets you become a vendor of tools used by agents instead of humans, and, from the agent side, it lets you dynamically add capabilities to your agent without writing new code: you just connect it to another MCP server. Examples of what an MCP server might provide: creating slides, interacting with a Git repo, searching documentation, checking the weather, pretty much anything you would normally write software to do.

Tool call: McpCall
Final answer: The Agents SDK’s `Runner` is essentially a turn-based orchestration loop:

1. Call the active agent’s model with the accumulated conversation.
2. Inspect the model response:
   - Final answer: validate output guardrails and return a `RunResult`.
   - Tool calls: run the tools, append their outputs to the conversation, then call the model again.
   - Handoff: switch the active agent to the selected specialist and continue.
3. Repeat until a final output is produced, a guardrail trips, or `max_turns` is exceeded.
