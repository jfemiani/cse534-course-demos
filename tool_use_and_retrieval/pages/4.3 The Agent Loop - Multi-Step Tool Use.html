Suppose you want an agent that can answer "When can I meet Professor Femiani in person this week?" To answer that, the agent needs two separate facts: his office hours, and his room number. The model has no way to know either one from training. It was not trained on this week's schedule, and it cannot look up a room number on its own, so it has to reach for tools for both. That is nothing new; the last lesson already covered one tool, one question.

What is new is that one tool is not enough here. The model has to call one tool, read what it returns, decide it still does not have everything it needs, call a second tool, and only then write an answer. It has to keep going through that call-observe-decide cycle for as many steps as the question needs, not just one.

This repeated cycle has a name in two different communities. OpenAI's documentation calls it the agent loop. The research paper that first described it calls it ReAct, short for Reason and Act (Yao et al., 2022). Both names describe the same thing.

Before running any of the three demos below, install this module's dependencies once: pip install -r requirements-tool-use-and-retrieval.txt (see requirements-tool-use-and-retrieval.txt).

The demo: let the Agents SDK run the loop

Writing that loop by hand is not hard for two tools, but it is the same handful of steps every time: check what the model asked for, run the matching function, send the result back, repeat. The OpenAI Agents SDK is a library that packages up exactly that pattern, so you describe the pieces once and let the SDK drive the loop.

The word "agent" gets used loosely in the field to mean almost anything that calls tools on its own. The SDK gives it a precise, narrower meaning, split across two objects with different jobs:

An Agent is not a loop, and it does not run anything by itself. It is a configuration: which model to call, its instructions (the system-prompt-style text telling it how to behave), and the list of tools it is allowed to use. Creating one makes no API call at all; it is closer to a job description than a running process.

A Runner is what actually executes a conversation with an Agent. Given an Agent and a question, it is the piece that calls the model, checks whether the response is a final answer or a request to call a tool, runs that tool if so, sends the result back, and repeats. It would be tempting to summarize this as "the Agent is the loop, the Runner just executes the tools," but that gets both halves wrong: the loop itself lives in the Runner, not the Agent, and the Runner is doing more than executing tools, since it is also the thing making every one of those repeated model calls.

This demo gives the model two tools, lookup_office_hours and lookup_room_number, and asks the two-part question above. Each tool is a plain Python function decorated with @function_tool from the Agents SDK; handing both tools to an Agent and calling Runner.run_sync(...) (the synchronous entry point; the SDK also has an async version, but this keeps the demo free of async/await) runs the entire call-observe-decide cycle in one line. This is the version to default to: for any task past a single tool call, the Agents SDK is doing real work for you, not just saving typing.

02a_agent_loop_agents_sdk.py (full source on GitHub)

Both tools are ordinary Python functions; the @function_tool decorator is what turns each one into something an Agent can call, reading its schema straight off the type hints and docstring, the same way it did in the @function_tool demo from the last lesson (demo 1c).

Both tools go into one Agent, and Runner.run_sync(...) is the entire loop: it calls whichever tool the model asks for, feeds the result back, and repeats until the model has enough to answer the question.

result.new_items is the step-by-step record the SDK kept while it ran the loop; walking it is how you see both tool calls it made along the way, not just the final answer.

Seeing the mechanism: the loop, hand-rolled

It is worth seeing the loop written out once, so "the Agents SDK runs the loop for you" is not a black box. This variant calls the plain Responses API directly: it checks response.output for a function_call item, runs the matching Python function, sends a function_call_output item back, and repeats until the model stops asking for tools. It trusts the model to stop on its own; production code typically adds a maximum step count as a safety net, so a confused model cannot loop forever.

Both tools' schemas are hand-typed here, the same way 1a typed count_letter's schema by hand, just doubled since there are two tools this time.

Here is the loop the Agents SDK was hiding: a while that keeps checking response.output for a function_call, runs the matching Python function, sends a function_call_output back tagged with previous_response_id, and only stops once the model quits asking for tools.

Mixing your own tools with hosted tools

An Agent's tools=[...] list is not limited to functions you wrote. WebSearchTool() wraps one of OpenAI's built-in tools: it is hosted (cloud-run), meaning OpenAI runs the search itself, so no code on your side executes for that call. Handing the SDK a list with both kinds, [lookup_room_number, WebSearchTool()], changes nothing about the loop: Runner.run_sync(...) still calls whichever tool the model asks for, local or hosted, and keeps going until the model has an answer.

This demo asks one question that needs both: a room number from the local tool and a real news story from the hosted one, so the two kinds of tool call show up side by side in the same run.

The only change from 02a's Agent is what goes in tools=[...]: one function tool next to one hosted tool, side by side in the same list.

type(item.raw_item).__name__ is how the trace tells the two kinds of tool call apart: a local @function_tool call and a hosted WebSearchTool() call show up as different item types, even though both came out of the same tools=[...] list.

Other ways to skip writing the loop

OpenAI's Responses API also runs an equivalent loop internally whenever you use one of its built-in tools, without the Agents SDK at all: you describe the tools you want available and the API keeps calling them until it has an answer. Reach for whichever is the smallest fit for the task: built-in tools directly on the Responses API for a single hosted capability, the Agents SDK once you have your own tools or more than one agent (or want to mix your own tools with hosted ones, as above), and the hand-rolled loop only when you need to see or control the mechanism directly.
