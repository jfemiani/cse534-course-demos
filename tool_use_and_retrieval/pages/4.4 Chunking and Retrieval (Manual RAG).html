A document too big to paste into a prompt

A model can only read as much text as fits in its context window. A syllabus, a textbook, or a codebase is usually much bigger than that. The common fix is to split the document into small pieces, called chunks, and only paste in the chunks that actually answer the question being asked.

Picking which chunks to paste in is the retrieval part of "retrieval-augmented generation." The model's final answer is generated the normal way; what changes is that the prompt now includes a small, relevant slice of a much larger document, chosen automatically.

How the chunks get chosen

Each chunk is converted into a list of numbers called an embedding, using a model trained on huge amounts of text so that chunks with similar meaning end up with similar numbers. The question gets embedded the same way. Comparing the question's embedding against every chunk's embedding ranks the chunks by how closely they match the question.

The comparison is the same dot-product idea from the multivariate normal lesson: divide each vector by its length to get a unit vector, and the dot product of two unit vectors, called cosine similarity, is 1.0 when they point the same way and 0 when they are unrelated. The closest chunk, or the closest few, get pasted into the prompt.

The demo

This demo chunks four short sentences about the course, embeds them, embeds a question, and pastes in whichever chunk scores highest before asking the model to answer.

Building this by hand vs. using the built-in tool

Writing the chunk-embed-rank pipeline yourself, as above, is useful for seeing what retrieval actually does. For real documents, OpenAI's Responses API includes a file_search tool: upload documents to a hosted vector store, attach that store to the API call, and the chunking, embedding, and ranking happen for you. Prefer the built-in tool once the concept makes sense.
