Two ways to rank the same documents

The last lesson ranked document chunks by embedding similarity. That is not the only way to rank them. Keyword search ranks by exact word overlap between the question and each chunk, the same idea search engines used long before embeddings existed. Vector search and keyword search usually agree, but not always, and the cases where they disagree are worth seeing directly.

Where vector search struggles

Embeddings capture meaning, not exact spelling. Two short codes like LAB-3042 and LAB-4071 look almost identical to an embedding model: same format, same length, same surrounding words. A question asking specifically about LAB-4071 can end up scoring both codes almost equally under vector search, even though only one of them is the right answer. Keyword search does not have this problem. It checks for the exact string and finds it immediately.

This is a general pattern, not a quirk of this example. Vector search is strong at matching meaning and paraphrase. Keyword search is strong at matching exact identifiers: product codes, function names, error messages, ticket numbers. Most production retrieval systems now combine both, a setup usually called hybrid search.

One more option: graph-based retrieval

A newer approach, usually called GraphRAG, builds a graph of entities and how they relate to each other instead of (or alongside) a set of embeddings, and answers a question by walking that graph. It can do better than plain vector search on questions that need to combine facts spread across many documents, but building and keeping the graph up to date costs real engineering effort. This course does not build a GraphRAG demo. If a project needs it, start with Microsoft's public GraphRAG project page linked below.

Making retrieval smarter: reranking and query rewriting

Vector and keyword search both score every chunk on its own: each chunk gets one number, computed by comparing it to the question, and nothing more. That one number can be misleading, since two chunks with a similar score can differ a lot in whether either one actually answers the question. Reranking adds a second pass to fix this. The initial search still runs first and returns a short list of candidates, say the top 20, but then a slower model reads the question and each candidate together, one pair at a time, and scores that pair directly instead of comparing two separately computed numbers. This second model, called a cross-encoder, is far more accurate at telling close candidates apart, but it is too slow to run against an entire document collection, which is why it only reranks the shortlist the first search already narrowed down. Fast-and-broad, then slow-and-precise, is the two-stage pattern most production retrieval systems use.

The other lever is the query itself. What someone actually types is not always a good search query: it can be short, vague, or worded differently than the documents that would answer it. Query rewriting expands or clarifies the question before it is embedded or searched. A different technique, called HyDE (Hypothetical Document Embeddings), has the model write a plausible-looking answer to the question first, then embeds that hypothetical answer instead of the question itself. A fabricated answer tends to share more wording and vocabulary with a real matching document than the original, terse question does, so searching with it can retrieve better matches, even though the hypothetical answer is never shown to the user.

Retrieval as one step in the agent loop

Everything in this lesson so far treats retrieval as a single lookup: search once, get chunks, answer. It does not have to stop there. Once a search is wrapped in a function tool, the agent loop from the previous lesson lets the model decide to search again with a narrower query if the first results were not enough, or search a summary first and only pull the full section if it turns out relevant. Wiring a retrieval tool into that same tool-calling loop, so the model can evaluate what came back and decide whether to search again, rerank, or answer, is usually called agentic RAG. It is not a new retrieval mechanism, just the tool-calling loop already covered, applied to a search tool instead of a lookup tool.
