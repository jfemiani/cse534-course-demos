A model can only read as much text as fits in its context window. A syllabus, a textbook, or a codebase is usually much bigger than that, so the common fix is to split it into small pieces, called chunks, and only paste in the chunks that answer the question being asked.

This pattern is retrieval-augmented generation, or RAG: retrieve the relevant chunks first, then generate the answer the normal way, with those chunks pasted into the prompt. The point is grounding. Asked about material it never saw during training, or that changed since, a model will otherwise guess, and a fluent, confident guess that is simply wrong is a hallucination. Retrieved chunks give the model something real to answer from instead.

How the chunks get chosen

An embedding turns a chunk of text into a vector of numbers, chosen so that chunks with similar meaning end up with similar vectors. Each chunk is embedded once, up front; the question is embedded the same way when it is asked. To compare two vectors, divide each one by its length so it has length 1, then take the dot product of the two: this is called cosine similarity, and it is 1.0 when the vectors point the same way, 0 when they are unrelated, and negative when they point in opposite directions. The chunk (or chunks) whose vector is most similar to the question's vector gets pasted into the prompt.

This module is API-focused rather than theory-focused: it treats the embedding model as something you call, the way the math modules treat a distribution as something you derive. If time allows later in the course, we will look at one way to build embeddings yourself, to make the idea concrete. A simple one: count how often each token in a fixed vocabulary appears in a chunk, giving one long vector of raw counts (50,000 numbers for a 50,000-token vocabulary), then use SVD (Singular Value Decomposition) directly on those count vectors to project them down to a much smaller vector, large enough to still capture meaningful differences between chunks. This method is called LSA (Latent Semantic Analysis). Applying SVD to the mean-centered version of that same count matrix would recover the same directions as the eigenvectors of the covariance matrix from the multivariate normal lesson's PCA; LSA just skips that centering step. This is not what OpenAI or other providers actually use for their embedding models; those are trained with deep learning, not built from token counts and SVD. But it is a self-contained way to see where an embedding's numbers could come from, without needing to train a neural network first.

Cutting the document in the first place

The demo above skipped the hardest part of chunking: it started with four chunks that were already short, complete sentences. A real document does not arrive pre-cut, and the cutting itself changes what retrieval can find. The simplest approach, fixed-size chunking, just counts out a fixed number of characters or tokens and cuts there, with no regard for where a sentence or paragraph happens to end. It is fast and needs no understanding of the text, but a chunk boundary landing mid-sentence can separate a fact from the words that explain it, and either half on its own embeds poorly.

A common fix for the boundary problem is overlap: instead of starting the next chunk exactly where the last one ended, back up a little and let the two chunks share some text. A fact that gets split across a boundary in one chunk still appears whole in its neighbor. Overlap does not stop the cutting from being blind; it just gives a fact more than one chance to land inside some chunk in one piece.

A more careful approach cuts on the document's own structure instead: try a paragraph break first, and only fall back to a sentence break, then a hard character cut, if a piece is still too big to fit. This is sometimes called recursive chunking, because the same rule is applied again to whatever piece did not fit the level above. Frameworks that build RAG pipelines, such as LangChain, ship a version of this as their default splitter (RecursiveCharacterTextSplitter) for exactly this reason: it is a better default than a blind fixed-size cut, without requiring an LLM call to decide where to split.

Chunking code is a different problem

Prose has paragraphs and sentences as natural units. Source code does not; its natural units are functions, classes, and blocks, and none of them are marked by a blank line the way a paragraph is. Splitting a Python file every N lines, the code equivalent of fixed-size chunking, will eventually cut a function's signature and docstring into one chunk and its body into the next, and neither half explains the other on its own.

Because code has an exact, parseable grammar, a better cut is available: parse the file and split on the syntax tree instead of on line counts, so each chunk is one complete function or class. Python's own standard library can do this without any extra dependency, using the ast module to walk the file's structure and ast.get_source_segment to recover the exact source text for each function or class. Tools built specifically for chunking code, such as LangChain's RecursiveCharacterTextSplitter.from_language(Language.PYTHON), automate the same idea for a range of programming languages.

Building this by hand vs. using the built-in tool

Writing the chunk-embed-rank pipeline yourself, as in Demo 3a, is useful for seeing what retrieval actually does. For real documents, OpenAI's Responses API includes a file_search tool: upload documents to a hosted vector store, attach that store to the API call, and the chunking, embedding, and ranking happen for you.

The built-in tool is not chunking-strategy-free, though; it is just chunking a fixed way by default. Uploading a file to a vector store without extra arguments uses an auto strategy that is a fixed-size cut much like Demo 3b's overlap strategy: 800-token chunks with 400 tokens of overlap. A static chunking strategy lets you set both numbers yourself when you attach a file. What the tool does not offer is paragraph-, sentence-, or code-aware cutting. That is still something to do before a file ever reaches the API, the way Demos 3b and 3c do it by hand. Prefer the built-in tool once the chunking concept makes sense, and revisit hand-rolled chunking only if the default 800/400 cut is measurably hurting retrieval on a real document.
