# 05b: The same verifier idea, applied to a floor plan instead of a number

Concept: `05_math_verifier.py` checked a number against a ground truth.
Not every task has a single correct value to compare against, but many
still have a precise, checkable specification. A floor plan is one: two
rooms may not occupy the same space, and every room needs at least one
door. Neither of those is a matter of opinion, so neither needs a metric
formula or a second model to check it — a direct geometric computation
settles both, in the same style used to check math answers or run a
formal proof through a theorem prover.

## What the demo does

1. Defines `rooms_overlap`, an axis-aligned rectangle overlap test: two
   rectangles conflict only if they overlap on both axes, so rooms that
   merely touch along a shared wall are not flagged.
2. Defines `shares_wall`, which confirms a proposed door actually sits on
   an edge the two rooms share, instead of trusting the input blindly.
3. Defines `verify_floorplan`, which checks every pair of rooms for
   overlap, checks every door against `shares_wall`, and confirms every
   room has at least one door.
4. Runs that verifier against three floor plans: one valid, one with two
   overlapping rooms, and one where a room has no door at all.

## Reading the result

```
--- valid layout: PASS ---

--- overlapping rooms: FAIL ---
  rooms overlap: 'bedroom' and 'bathroom'

--- room with no door: FAIL ---
  room has no door: 'bathroom'
```

Both failures are the kind of mistake a fluent-sounding description
could easily hide: a paragraph describing "a cozy bedroom next to the
bathroom" says nothing about whether their rectangles actually overlap
by a foot, and nothing about whether the bathroom got a door in the
final layout. A geometric check catches both without needing to
understand the description at all — it only needs the coordinates.

## Why this matters beyond one demo

This is the same **Reinforcement Learning with Verifiable Rewards
(RLVR)** idea `05_math_verifier.py` covered, applied outside math and
code. The requirement for a verifier is not "the task is math" — it is
"the specification is precise enough to check by computer." A floor
plan generated by an LLM (as text, an SVG, or a structured JSON layout)
can be turned back into rectangles and doors, and then checked exactly
this way: no overlaps, every room reachable. Any domain with a
checkable specification — physical layouts, schedules with no
double-bookings, code with passing tests, proofs a theorem prover
accepts — can plug into an RL training loop the same way DeepSeek-R1
used a rule-based math and code checker, or AlphaProof used the Lean
theorem prover (see `05_math_verifier.md` for both citations). Where no
such specification exists, this approach has nothing to check, and the
page's earlier tools (BLEU-style metrics, LLM-as-judge, human
preference) are what is left.

## Endpoint

No API calls. Pure geometry, computed locally on hardcoded room
coordinates.

## Regeneration prompt

If this needs to be regenerated, ask an LLM assistant: "Represent rooms
as axis-aligned rectangles (x1, y1, x2, y2) and doors as pairs of room
names that share a wall. Write `rooms_overlap` (true only if two
rectangles overlap on both axes, not just touch), `shares_wall` (true if
two rectangles share an edge), and `verify_floorplan` (checks every pair
of rooms for overlap, checks every door sits on a shared wall, and
checks every room has at least one door). Run it against a valid floor
plan, one with an overlap, and one with a missing door, and print
PASS/FAIL with the specific violations for each."
