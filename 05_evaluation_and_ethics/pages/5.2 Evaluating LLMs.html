Module 3 built a small (trivial!) language model using n-grams and gave you a way to measure surprise. Module 4 gave you ways to customize an LLM through custom instructions, tool use and retrieval. This lesson asks the question you should ask about anything you build: is it any good?

That question splits into two. Sometimes you want to measure a model's raw ability. That is a benchmark. Sometimes you want to measure a choice you made while building something on top of a model, such as which retrieval strategy to use. That is an ablation study or a grid search. Both count as evaluation. This lesson covers both, starting with something you already built.

Evaluating a model you already built

Lesson 3.4 defined cross-entropy: the average surprise a model feels when it sees real data. A model that is never surprised has low cross-entropy. A model that keeps getting caught off guard has high cross-entropy.

Lesson 3.5 built an n-gram model. It predicts the next character from the last few characters it has seen. That context length is called the model's order. Until now, you only watched it generate text. This demo does something different. It holds out some text the model never trained on. Then it measures cross-entropy on that held-out text instead.

Cross-entropy is measured in bits, which is not the most intuitive unit. A second, more readable number is perplexity. This lesson uses the convention perplexity = 2 raised to the cross-entropy, when cross-entropy is measured in bits. (If you see cross-entropy reported in nats instead of bits, the matching formula is perplexity = e raised to the cross-entropy. Either convention is standard, and equivilent as long as the base of the logarithm and the exponent match.) A perplexity of 8 means the model is, on average, about as unsure as if it were guessing uniformly among 8 equally likely next characters.

The demo below trains the n-gram model three times, once for each of three orders. Each time, it reports cross-entropy and perplexity on the same held-out text. Varying one setting and comparing the results is already a small controlled comparison: order is the one parameter being swept, and nothing else changes between runs. Later in this lesson, that same idea gets a name: a grid search.

Read the "miss rate" column first. It says how often the held-out text contained a context the model never saw during training. At order 2, almost every two-character context has already shown up during training, so the miss rate stays low. At order 8, most eight-character contexts in new text are new to the model, so the miss rate climbs past 60%. When the model misses, it falls back to a small floor probability instead of a confident guess. That fallback is expensive. A wrong guess made with high confidence produces a large surprise. That is exactly the point lesson 3.4 made about surprise and rare events. This is why order 8's perplexity is so much worse here, even though it "knows more" in the sense of having memorized far more contexts. A short context generalizes. A long context memorizes, and text it has not memorized breaks it.

Reading a results table like a researcher

The table above already uses two conventions you will see in almost every AI paper. Look at the column headers again. The down arrow (↓) next to cross-entropy and perplexity means lower is better for that column. An up arrow (↑) would mean the opposite: higher is better. You will usually see accuracy or a benchmark score reported that way. A reader should never have to guess which direction is good; the arrow says it directly.

Now look at the numbers themselves. The best value in a column is bolded. The second-best is italicized. This lets a reader scan a large table full of numbers and immediately spot the winner in each column. They do not have to read every cell.

Here is the limitation this convention hides. A single run, like the one in the table above, is one sample. If you retrained the order-2 and order-4 models with a different train/held-out split, the two perplexity numbers might swap places, because they are close. Checking whether a small difference is a real improvement, or just noise, means running a large model many times. That is often too expensive to actually do. That is why a lot of published tables report a single run's numbers with no error bars at all. Treat a difference of a point or two on a benchmark table as informative, but not as proof that one model is truly better than another. This is a real limitation of how the field reports results, not a trick question.

Benchmarks for large, frontier models

The n-gram model above is small enough to evaluate by hand. The large models you use through an API are evaluated with standardized tests called benchmarks. A few benchmark families come up constantly. You should recognize their names, even though this page will not give you specific scores. Scores from large models change every few months. Any number printed here would be out of date within a year.

  • MMLU and MMLU-Pro test broad academic knowledge across many subjects, from history to physics.
  • GSM8K and AIME test math, from grade-school word problems to olympiad-level competition problems.
  • HumanEval and SWE-bench test code. HumanEval checks whether a model can write a short function correctly. SWE-bench checks whether a model can fix a real bug in a real open-source codebase.
  • GPQA tests graduate-level science questions, written to be hard to answer by search alone.

Rather than memorize numbers, look them up yourself when you need them. SWE-bench's leaderboards are a live example of a benchmark leaderboard you can check right now. Searching "MMLU leaderboard" or "livebench" will turn up other current comparisons. A table printed on this page would already be stale by the time you read it.

A different kind of leaderboard: head-to-head human judgment

LMArena (formerly known as LMSYS Chatbot Arena) measures something a benchmark cannot. A person is shown two anonymous answers to the same prompt, side by side, with no model names attached. The person picks the answer they prefer, or calls it a tie. Votes accumulate into a rating using the same Elo system used to rank chess players.

Notice what this measures. Compare it to what MMLU or GSM8K measure. Those benchmarks check whether an answer is factually or formally correct. LMArena checks whether people liked the answer better. That is a different question. A model can rank differently on the two kinds of leaderboard. Being correct and being preferred are not the same thing.

Benchmarks go stale

A benchmark's questions eventually end up online. Once that happens, those questions can get scraped into the training data of the next model. If that happens, a high score on the benchmark might mean the model memorized the answer, not that it solved the problem. This is called benchmark contamination. It is a documented, studied problem, not a rumor. See Xu et al., "Benchmark Data Contamination of Large Language Models: A Survey" (2024) for a real, citable overview of how this happens and how researchers try to detect it.

One response to this problem is to keep rotating in new questions instead of keeping a benchmark fixed forever. LiveBench is built this way. The idea is that a benchmark's newest questions have not had time to leak into anyone's training data yet.

Evaluating your own work: ablation studies and grid search

Benchmarks measure a model. Most of the time, you are not evaluating a whole model. You are evaluating a choice you made while building something on top of one. Two ideas cover almost every version of this.

An ablation study removes or changes one piece of a system. Then it re-measures the result, to find out what that piece was actually contributing. Maybe you added a sentence to a prompt because you thought it helped. An ablation study means running the system with and without that sentence. Then you check whether the results actually changed.

A grid search tries combinations of settings systematically, to find the best combination instead of guessing one. The n-gram demo above already did this with one setting: order. A grid search can sweep more than one setting at once, checking every combination.

Here is a second worked example, pulled from module 4. Which retrieval strategy actually works best for a small collection of documents: vector search, keyword search, or a hybrid of the two? Instead of guessing, this demo builds a small labeled test set: six questions, each paired with the one document that answers it. It measures hit-rate: how often the correct document showed up in the top results. The code below is available in full on GitHub at 02a_retrieval_eval_hitrate.py; we'll walk through the parts that matter.

The documents and questions are the test set itself, so getting them right matters more than any code around them. Each question names the exact index of the one document that should answer it, which is what turns "does this look about right" into something you can actually count.

The scoring loop is where the three strategies actually get compared: the same question is scored against every document three separate ways, and a strategy earns a hit only when the correct document lands in its own top two.

Two of the six test questions ask about near-identical assignment codes. Lesson 4.5 used this same kind of question to show where plain keyword search wins. Measuring hit-rate directly, instead of assuming vector search always wins, is the whole point. "Which retrieval strategy is actually better for my agent" is a question you can answer with a small table like this one. It does not have to be a guess.

Cherries, apples, and lemons: what a hit-rate hides

A hit-rate of 0.83 tells you vector search won on this test set. It does not tell you what that win actually looked like question by question. A second demo picks out three individual examples instead of one aggregate number: the best margin, the median margin, and the worst margin, by how far ahead the correct document's score was over the best-scoring wrong document. Borrowing produce-market language for it: the cherry is the best case, the apple is a fair, typical case, and the lemon is the worst case. The code is available in full on GitHub at 02b_retrieval_eval_examples.py; the two parts worth reading closely are the margin calculation and the selection itself.

The margin is what turns "hit or miss" into a number you can sort by: a large positive margin means the correct document won by a wide gap, and a negative margin means vector search actually liked a wrong document better.

Sorting by margin is what makes cherry, apple, and lemon well-defined instead of a judgment call: the top of the sorted list, the middle, and the bottom.

One run of that demo produced this:

example question vector search's top pick margin hit at K=2?
cherry"When can I stop by without an appointment?"office hours document (correct)+0.272yes
apple"What is the assignment code for LAB-4071?"LAB-4071 document (correct)+0.039yes
lemon"Do I need to sign in to class?"LAB-4071 document (wrong; correct one ranked 3rd)−0.025no

The cherry is a clean win: the correct document is close to a paraphrase of the question. The apple still wins, but barely — this is closer to what most of the "hits" behind that 0.83 actually looked like than the cherry is. The lemon is the one genuine miss behind that same 0.83: for a plain question about attendance, vector search's top pick was a sentence about a lab assignment code, and the sentence that actually answers the question ranked third. No person reading both sentences would make that mistake. This is what the section title means by "a hit-rate hides individual examples": the number said 0.83, and 0.83 is true, but it does not tell you that vector search failed here in a way a human would find obviously wrong. A measurement can be accurate and still do a poor job matching human judgment.

Notice the temptation sitting right here: it would have been easy to only show the cherry above, and this page would still be telling the truth, in the narrow sense that the cherry really did happen. That is cherry-picking — reporting your best example instead of a representative one — and it is a real risk in your own reports, not just a hypothetical one. It is worth developing the habit of asking, of your own results and of anyone else's: "is this the typical case, or is this the cherry?" A demo, a blog post, or a paper that shows only glowing examples earns exactly that suspicion.

A zoo of automatic metrics

Hit-rate and perplexity are two metrics out of a much larger set that shows up constantly in papers and leaderboards. The most common one for scoring generated text against a reference answer is BLEU, borrowed from machine translation. BLEU counts overlapping runs of words between a candidate and a reference; it has no idea what the words mean. The code below is available in full on GitHub at 03_bleu_score.py; the part worth reading is the scoring loop itself.

The three candidates are chosen to expose exactly what BLEU cannot see: a correct paraphrase that shares almost no words with the reference, and a factually wrong sentence that shares almost every word.

One run of that demo produced this:

candidate BLEU ↑
exact match1.000
wrong room, high overlap0.919
good paraphrase, low overlap0.078

Read that middle row carefully: a sentence with the wrong room number scores nearly as high as an exact match, while a correct paraphrase scores far lower than either. BLEU rewarded the wrong answer over the right one, for the same reason the lemon above happened: a metric can be precisely defined and consistently computed while still measuring something other than "is this actually a good answer." This is not a reason to distrust every metric equally, but it is a reason to know which metric you are reading and what it can and cannot see before treating its number as the last word.

BLEU is one entry in a larger zoo, each trading off cost, speed, and how closely it tracks human judgment:

  • ROUGE scores n-gram and longest-common-subsequence recall instead of precision. Standard for summarization, where the question is closer to "did the summary keep the important parts" than "did it use the exact same words."
  • METEOR matches synonyms and word stems instead of requiring an exact string match, specifically to reduce the paraphrase problem the table above shows.
  • Exact match / F1 is standard for extractive question answering (e.g. the SQuAD benchmark), where the answer is a short span of text pulled directly from a document rather than a free-form generated sentence.
  • BERTScore replaces word overlap with embedding similarity between candidate and reference tokens, so a correct paraphrase scores well instead of being penalized the way it is here.
  • LLM-as-judge replaces the formula entirely: a separate, usually stronger, model reads the candidate and reference and scores or ranks the answer. It tracks human judgment more closely than word-overlap metrics, at the cost of being slower, more expensive, and dependent on whichever model is doing the judging.

No single metric here is "the" right one. Knowing which metric a paper or leaderboard reports, and what that metric is blind to, matters as much as the number itself.

Tools that do this for you

You will not build every evaluation pipeline by hand. A few tools exist specifically for this, and this list will change faster than this page can track, so treat these as starting points to search from rather than a fixed recommendation.

  • OpenAI Evals is a framework for defining test cases and running them against a model automatically.
  • Anthropic publishes its own guidance on building evaluations, including tooling built into the Anthropic Console.
  • promptfoo is a widely used open-source tool for testing and comparing prompts and models side by side. Tools like Langfuse add tracing on top of that, so you can see exactly what a multi-step agent did before it produced a given answer.
