Module 3 built a small (trivial!) language model using n-grams and gave you a way to measure surprise. Module 4 gave you ways to customize an LLM through custom instructions, tool use and retrieval. This lesson asks the question you should ask about anything you build: is it any good?

That question splits into two. Sometimes you want to measure a model's raw ability. That is a benchmark. Sometimes you want to measure a choice you made while building something on top of a model, such as which retrieval strategy to use. That is an ablation study or a grid search. Both count as evaluation. This lesson covers both, starting with something you already built.

Evaluating a model you already built

Lesson 3.4 defined cross-entropy: the average surprise a model feels when it sees real data. A model that is never surprised has low cross-entropy. A model that keeps getting caught off guard has high cross-entropy.

Lesson 3.5 built an n-gram model. It predicts the next character from the last few characters it has seen. That context length is called the model's order. Until now, you only watched it generate text. This demo does something different. It holds out some text the model never trained on. Then it measures cross-entropy on that held-out text instead.

Cross-entropy is measured in bits, which is not the most intuitive unit. A second, more readable number is perplexity. This lesson uses the convention perplexity = 2 raised to the cross-entropy, when cross-entropy is measured in bits. (If you see cross-entropy reported in nats instead of bits, the matching formula is perplexity = e raised to the cross-entropy. Either convention is standard, and equivilent as long as the base of the logarithm and the exponent match.) A perplexity of 8 means the model is, on average, about as unsure as if it were guessing uniformly among 8 equally likely next characters.

The demo below trains the n-gram model seven times, once for each order from 2 through 8. Each time, it reports cross-entropy and perplexity on the same held-out text. Varying one setting and comparing the results is already a small controlled comparison: order is the one parameter being swept, and nothing else changes between runs. Later in this lesson, that same idea gets a name: a grid search.

The code below is available in full on GitHub at 01_ngram_eval.py; we'll walk through the parts that matter.

The part worth reading closely is what happens when a context has never been seen before: instead of crashing or guessing zero, the model falls back to a small floor probability. That fallback is what turns a rare context into an expensive surprise later in this page.

The sweep itself is a short loop: train fresh counts at each order, evaluate cross-entropy and miss rate on the same held-out blocks, and convert to perplexity.

The best order in this sweep is 3, not 2 or 8. That result is worth sitting with, because it is the first concrete example on this page of overfitting (also called overtraining): a model becoming so tuned to the specific contexts in its training data that it stops generalizing to text it has not seen, even though nothing about the training procedure told it to do that. Order 8 does not fail because it is a bad model in some vague sense. It fails because it memorizes long, specific eight-character contexts instead of learning the shorter, more common patterns that transfer to new text. Memorizing training data more precisely is not the same thing as understanding it, and cross-entropy on held-out text is exactly the measurement that tells the two apart. A cross-entropy computed on the training data itself would not catch this at all; order 8 would look like the best model in the world, because it has essentially copied down the answers.

This is a specific case of a more general shape called the bias-variance tradeoff. A short context like order 2 underfits: it is too simple to capture patterns that really are there, so it is consistently a little wrong in the same ways no matter what training data it saw (that consistent kind of error is called bias). A long context like order 8 overfits: it is flexible enough to fit its own training data almost exactly, but that same flexibility means a different training sample would have produced a noticeably different model, so its predictions on new text swing wildly depending on which contexts it happened to memorize (that sensitivity to the particular training sample is called variance). Order 3 sits closer to a sweet spot between the two. A sweep across every order in between, rather than only the two extremes, is what makes that interior optimum visible at all — checking only order 2 and order 8 would show a large gap between them, but nothing that points to 3 as the actual best choice.

One more note before moving on: order 8's miss rate climbs past 60%. That miss rate measures how often a held-out context was never seen in training, and every miss falls back to the same small floor probability instead of a confident guess. A wrong guess made with high confidence produces a large surprise. That is exactly why order 8's perplexity is so much worse here, even though it has memorized far more contexts than order 2 or 3. A short context generalizes; a long context memorizes, and text it has not memorized breaks it.

Cherries, apples, and lemons: what a single average hides

Table 1 reports one cross-entropy number for order 3, averaged over 723 held-out blocks of text. However, this single number can hide what is really happening in the model. A second demo drills deeper into that number: it scores each individual held-out block of text on its own and sorts the results, so you can look at the best, the median, and the worst block directly, as actual text instead of a single figure.

The code is available in full on GitHub at 01b_ngram_block_scores.py.

Scoring one block needs nothing beyond the cross-entropy already defined above. Rather than averaging the cross entropy over the entire corpus, it computes it over the characters of one text-block at a time.

Sorting the held-out blocks by that score directly is what turns "best," "typical," and "worst" into an exact position in a list instead of a judgment call.

Scan the cherries and lemons again, not just their scores but the text itself: what do you notice? Three of the five cherries are the identical block, "PETRUCHIO:", and three of the five lemons are the identical block, "PROSPERO:" — the training text turns out to contain several blank-line-separated blocks that are nothing but a bare speaker name. Both names are nearly the same length, so why does one score so much better than the other? Which of the two characters would you expect to speak more often elsewhere in the training data, and what would that mean for how familiar the order-3 model is with the letter-to-letter transitions inside that name? Now look at the apples: none of them are bare names, and every one is a full sentence or more. Their cross-entropy sits close to the corpus-wide average of 2.791 bits. Given all that, which group — cherries, apples, or lemons — do you think looks most like a typical block of held-out text, and which two are really telling you about something other than how well the model writes?

The examples in Table 2 show us something that the single averaged numbers shown in Table 1 cannot: the cherries are suspiciously easy in a way that has nothing to do with the model being good. A block that is just "PETRUCHIO:" has almost no characters left to get wrong, so of course its cross-entropy is low! The model is barely being tested. This model's training does not optimize for that number directly. Counting how often a character follows a given context is nothing like searching for the lowest possible cross-entropy. Table 1's order sweep did, though: order 3 won because it scored lowest. Suppose that same kind of selection also decided how long a generated passage runs. Short, common words would beat long, informative ones every time, because fewer characters mean fewer chances to be surprised. That is a cheaper route to a low score. It has nothing to do with writing better text. That failure mode has a name, Goodhart's Law: "when a measure becomes a target, it ceases to be a good measure." Cross-entropy stops being a good measure of a model's held-out performance exactly when something starts optimizing for the number instead of the writing quality it was supposed to stand in for. That something can be a selection process like Table 1's order sweep. It can also be your own choice of which examples to report. The cherries are a case of the second one: a reminder to check what a metric actually rewards before you trust it.

Reading a results table like a researcher

Table 1 already uses two conventions you will see in almost every AI paper. Look at the column headers again. The down arrow (↓) next to cross-entropy and perplexity means lower is better for that column. An up arrow (↑) would mean the opposite: higher is better. You will usually see accuracy or a benchmark score reported that way. A reader should never have to guess which direction is good; the arrow says it directly.

Now look at the numbers themselves. The best value in a column is bolded. The second-best is italicized. This lets a reader scan a large table full of numbers and immediately spot the winner in each column. They do not have to read every cell.

Here is the limitation this convention hides. A single run, like Table 1 above, is one sample. If you retrained the order-2 and order-4 models with a different train/held-out split, the two perplexity numbers might swap places, because they are close. Checking whether a small difference is a real improvement, or just noise, means running a large model many times. That is often too expensive to actually do. That is why a lot of published tables report a single run's numbers with no error bars at all. Treat a difference of a point or two on a benchmark table as informative, but not as proof that one model is truly better than another. This is a real limitation of how the field reports results, not a trick question.

Intrinsic versus extrinsic evaluation

Intrinsic evaluation measures whether a model has learned to follow the rules of the data itself: does its predicted distribution over next characters match the real distribution found in held-out text? Cross-entropy answers exactly this question, checked one true next-character at a time. This is the fundamental goal of generative AI. "Generative" means modeling the true distribution of the data closely enough to draw new, realistic samples from it. But following the distribution is usually a means to an end, not an end in itself. Nobody actually wants a model that fits Shakespeare's distribution for its own sake. They want to write, answer, summarize, or translate with it. That gap, between the fundamental objective and the actual use, is why a second kind of evaluation exists. Every number on this page so far, Table 1 and Table 2 both, is intrinsic evaluation.

Extrinsic evaluation measures the other side of that gap: can the model solve a task, period. Give it one input — a prompt — let it generate one specific output, and ask how good that particular output is at solving whatever the task actually is, usually by comparing it to a reference answer or a human judgment. There is no probability involved at all: a non-probabilistic, rule-based system could be scored exactly the same way. This is much closer to a regression problem, how far is this one output from the target, than to fitting a distribution.

Generative AI leans on intrinsic evaluation more than most of machine learning, and that is not an accident: fitting the distribution of the training data as well as possible is most of what makes these models useful in the first place. Getting good at that one intrinsic objective, "predict the next token well," turns out to also produce a model that can, as a side effect, follow instructions, translate, summarize, answer questions, and write code — a genuinely diverse set of tasks, none of which cross-entropy was ever asked about directly. That side effect is a large part of why the field is willing to train on nothing but next-token prediction at massive scale.

Even so, once you actually want to use the model for one of those tasks, the question you care about is extrinsic: did it solve this task, not "does it model language well in general." Most evaluations that you will actually run day to day are extrinsic, including almost everything left on this page. For language, there are several different ways to measure whether an output solved the task. The rest of this page builds exactly that comparison, starting with the order sweep from Table 1.

A zoo of automatic metrics

Extrinsic evaluation has a much larger set of metrics than intrinsic evaluation, because there are many different ways to measure how close a generated output is to a reference. These show up constantly in papers and leaderboards for scoring generated text against a reference answer. Every one of these has a mature library implementation you can call directly.

LLM-as-judge: asking a model instead of counting words

Every metric above works from the outside: it counts overlapping words or subsequences and never actually reads the candidate for meaning. All of them also needed one more thing you may not have noticed: a single "true" continuation to compare against. That works for continuing Shakespeare, where the held-out text supplies exactly one real continuation. It stops working the moment a task has more than one acceptable answer, which is most tasks. Two students can answer the same question correctly in different words, and no word-overlap formula can tell you that.

LLM-as-judge replaces the formula entirely: a separate model reads the question, a reference answer, and a candidate, and reports a judgment directly, based on meaning rather than word overlap. To show what that buys you, the rest of this section switches to a plain question-answering example, "when and where are office hours," where a wrong word (the room number) and a differently-worded but correct answer are easy to tell apart by hand, so you can check the judge's calls yourself. The code is available in full on GitHub at 04_llm_judge.py.

The judgment itself is a small structured-output object, the same pattern "Demo 6: Structured Output with Pydantic" used back in module 2: a boolean for whether the answer is correct, a 1-to-5 quality score, and a one-sentence reason, so the result is something you can put in a table instead of free text you have to re-read every time.

The prompt is where the strictness actually comes from: it tells the judge model explicitly to check factual details like room numbers, rather than trusting it to notice on its own.

The judge calls the good paraphrase correct, the same quality score as the exact match, even though BLEU gave it only 0.078. That is a full reversal of BLEU's ranking, and it happened because the judge reads for meaning instead of counting words. This is not free: every judgment here is a full model call, slower and more expensive than a formula, and only as good as the model doing the judging. A weaker judge model or a vaguer prompt can miss the same mistake a strong judge just caught. That tradeoff is why word-overlap metrics like BLEU still get used alongside LLM-as-judge instead of being replaced by it.

Three candidates against one reference answer is a controlled setting: the judge always has a clear right answer to check against. Not every use of LLM-as-judge has that. A different, equally common question has no single reference answer at all: which of two prompts gets better answers out of the same model? The code is available in full on GitHub at 04b_llm_judge_prompt_compare.py; it answers a small set of questions two ways and asks a judge to pick the better answer each time.

The model is given a source of information to answer from: a short syllabus-style blurb covering office hours and homework policy, hardcoded directly into the prompt template as {context} (visible in the snippet below). There is no retrieval step here, no search over a document collection to find the relevant chunk; the whole blurb is simply always present. That means this is not testing RAG. It is testing something narrower: given the right information already sitting in the context, does the model actually use it correctly? Needle in a haystack: testing one specific capability

Every metric on this page so far scores a whole answer or a whole continuation. A needle-in-a-haystack test asks a narrower question: can a model find and use one specific fact, planted somewhere inside a much longer context?

The setup is simple. Take a long document, "the haystack," and insert one sentence, "the needle," at some position inside it: the beginning, the middle, the end. Then ask a question only that sentence can answer, and check whether the model's answer is correct. Repeating this at many needle positions, across contexts of many lengths, produces a grid: for each position and length pair, did the model find the needle?

That grid is what these tests are actually built to catch. A model can advertise a context window of 128,000 tokens and still fail to use most of it. Some models answer reliably when the needle sits near the start or end of the context, but miss it when the needle sits in the middle. Researchers call that failure pattern "lost in the middle." A pass rate near 100% everywhere means the model actually uses its whole advertised window. A pass rate that drops in the middle of the grid means the advertised window and the usable window are two different numbers.

This is not a general-purpose quality metric, and it is not meant to be one. It checks one specific capability: whether a model actually uses the context length it claims to support. Table 1's order sweep checked a similarly narrow capability of the n-gram model, how much context length helped or hurt, instead of measuring some general notion of "good text." A model can pass every needle-in-a-haystack test and still write poorly, and a model can fail one and still be a fine choice for short-context tasks that never approach its limit. The test is only useful for the question it was built to answer: given a context this long, does the model actually read all of it?

Evaluating your own work: ablation studies and grid search

Benchmarks measure a model on its own. Most of the time, you are not evaluating a whole model — you are evaluating a choice you made while building something on top of one. Two ideas cover almost every version of this: the ablation study and the grid search.

An ablation study removes or changes one piece of a system, then re-measures the result to find out what that piece was actually contributing. Maybe you added a sentence to a prompt because you thought it helped. An ablation study means running the system with and without that sentence, then checking whether the results actually changed. In practice, an ablation study usually runs backwards from how the system was actually built. Most projects start from a baseline — often someone else's published result — partly just to prove you can reproduce it and get a working system running before sticking your neck out too far. From there, a system improves through a series of educated guesses: try something, keep it if it helps, drop it if it doesn't. An ablation study is how you prove that story to somebody else afterward: for each guess you kept, show the result with it and without it, so a skeptical reader does not have to take your word for which changes actually mattered.

A grid search tries combinations of settings systematically, to find the best combination instead of guessing one. The n-gram demo above already did this with one setting: order. A grid search can sweep more than one setting at once, checking every combination — but the size of that grid grows exponentially with the number of settings you want to explore. Three settings with four values each is 64 combinations to run; five settings with four values each is over a thousand. Because of that, a full grid search over everything you are unsure about is rarely what actually gets run. A common compromise is a hierarchical (or greedy) search: fix your best guess for most settings, sweep only the one you are least confident about, lock in whatever wins, then sweep the next setting you are least sure of. This costs far less than a full grid, at the price of never checking combinations the hierarchy skips over. This general problem — searching over the settings a model or pipeline exposes — is usually called hyperparameter optimization, and libraries such as Optuna and Ray Tune automate smarter-than-grid strategies (e.g. Bayesian search) instead of the exhaustive or hand-rolled hierarchical sweep described here.

Benchmarks for large, frontier models

Everything above evaluated something small enough to build and measure by hand. The large models you use through an API are evaluated with standardized tests called benchmarks instead. A few benchmark families come up constantly. You should recognize their names, even though this page will not give you specific scores. Scores from large models change every few months. Any number printed here would be out of date within a year.

  • MMLU and MMLU-Pro test broad academic knowledge across many subjects, from history to physics.
  • GSM8K and AIME test math, from grade-school word problems to olympiad-level competition problems.
  • HumanEval and SWE-bench test code. HumanEval checks whether a model can write a short function correctly. SWE-bench checks whether a model can fix a real bug in a real open-source codebase.
  • GPQA tests graduate-level science questions, written to be hard to answer by search alone.

Rather than memorize numbers, look them up yourself when you need them. SWE-bench's leaderboards are a live example of a benchmark leaderboard you can check right now. Searching "MMLU leaderboard" or "livebench" will turn up other current comparisons. A table printed on this page would already be stale by the time you read it.

A different kind of leaderboard: head-to-head human judgment

LMArena (formerly known as LMSYS Chatbot Arena) measures something a benchmark cannot. A person is shown two anonymous answers to the same prompt, side by side, with no model names attached. The person picks the answer they prefer, or calls it a tie. Votes accumulate into a rating using the same Elo system used to rank chess players.

Notice what this measures. Compare it to what MMLU or GSM8K measure. Those benchmarks check whether an answer is factually or formally correct. LMArena checks whether people liked the answer better. That is a different question, close to the one the LLM-as-judge demo above asked, except here the judge is a person instead of a model. A model can rank differently on the two kinds of leaderboard. Being correct and being preferred are not the same thing.

Benchmarks go stale

A benchmark's questions eventually end up online. Once that happens, those questions can get scraped into the training data of the next model. If that happens, a high score on the benchmark might mean the model memorized the answer, not that it solved the problem. This is called benchmark contamination. It is a documented, studied problem, not a rumor. See Xu et al., "Benchmark Data Contamination of Large Language Models: A Survey" (2024) for a real, citable overview of how this happens and how researchers try to detect it.

One response to this problem is to keep rotating in new questions instead of keeping a benchmark fixed forever. LiveBench is built this way. The idea is that a benchmark's newest questions have not had time to leak into anyone's training data yet.

Tools that do this for you

You will not build every evaluation pipeline by hand. A few tools exist specifically for this, and this list will change faster than this page can track, so treat these as starting points to search from rather than a fixed recommendation.

  • OpenAI Evals is a framework for defining test cases and running them against a model automatically.
  • Anthropic publishes its own guidance on building evaluations, including tooling built into the Anthropic Console.
  • promptfoo is a widely used open-source tool for testing and comparing prompts and models side by side. Tools like Langfuse add tracing on top of that, so you can see exactly what a multi-step agent did before it produced a given answer.

Every demo on this page was written out explicitly rather than delegated to a library, on purpose: seeing the cross-entropy formula, the BLEU loop, or the verifier's answer-extraction logic written out is what makes it possible to say exactly what a metric can and cannot see. But it is worth seeing, at least once, how much of that explicit code a library like promptfoo would absorb. Our most significant demo on this page is the retrieval hit-rate comparison (02a_retrieval_eval_hitrate.py): a loop over six test questions, each checked against vector, keyword, and hybrid search, with hits and misses tallied by hand into the table shown earlier. The same idea, expressed as a promptfoo config instead of a Python loop, looks roughly like this (illustrative only — not run for this page):

providers:
  - file://retrieve.py   # wraps whatever search strategy you're testing: vector, keyword, or hybrid

tests:
  - vars:
      query: "What is the assignment code for LAB-4071?"
    assert:
      - type: contains
        value: "LAB-4071"
  - vars:
      query: "When can I stop by without an appointment?"
    assert:
      - type: contains
        value: "office hours"
  # ...one test case per question, one assert per expected document

Running promptfoo eval against a config like this checks every question against every provider and prints a comparison table automatically — the equivalent of the hand-built Table 6 above, without writing the loop, the tally, or the table formatting yourself. That is a real reduction in code for exactly this kind of check. The tradeoff is that the library makes assumptions about how your retrieval script is structured and how "hit" is defined (here, a substring match instead of the rank-based top-K logic our demo used); the hand-rolled version on this page is longer specifically so you can see, line by line, what "hit" means before a library decides that for you.

When you have a verifier: automatic reward instead of automatic scoring

The promptfoo config above still used a contains assertion — a substring check, one step more exact than BLEU but still a stand-in for "is this actually right." Some tasks do not need a stand-in at all. If a task's output can be checked against a precise, computable specification, a short program can decide correct or incorrect directly, with no metric formula and no second model forming an opinion. That kind of check is called a verifier, and it is the mechanism behind most of the current wave of "reasoning" models.

The clearest case is a math problem with a known numeric answer. The code below is available in full on GitHub at 05_math_verifier.py; it poses one word problem and checks four candidate solutions against the true answer, 20.

Two checks run independently: whether the solution used the expected #### answer marker, and what number the solution actually landed on. Running the demo produced this:

Table 7: verifying four candidate solutions to one math problem (ground truth: 20)
candidate format ok extracted accuracy reward
correct, well-formattedTrue20.0True
correct, no format markerFalse20.0True
wrong arithmetic, well-formattedTrue23.0False
correct, different formattingTrue20.0True

The format check and the accuracy check disagree on the second row, and that disagreement is deliberate. A solution that reasons correctly but forgets the expected answer marker is a formatting problem, not a correctness problem. Conflating the two would punish a right answer for a cosmetic reason. The third row is where a verifier earns its keep. That solution reads exactly as confidently as the correct ones, with nothing about its fluency signaling the arithmetic mistake. But the extracted number simply does not match. The fourth row is the flip side of the BLEU lesson earlier on this page: BLEU would score "$20.00" against a reference of "20" as a near-miss because the strings differ, while this verifier parses both as the number 20.0 and calls it correct — a verifier can be built to care about the value, not the wording.

This generalizes past math answers. DeepSeek-R1's training used exactly this kind of rule-based reward at scale: an accuracy reward from checking a final answer, plus a separate, smaller format reward, and a compiler-based check for coding problems (Guo et al., DeepSeek-AI, "DeepSeek-R1: Incentivizing Reasoning Capability in LLMs via Reinforcement Learning", 2025). DeepMind's AlphaProof pushes the same idea into formal mathematics: it generates proofs as sequences of Lean tactics, and every candidate proof is checked by actually running the Lean theorem prover, which accepts or rejects it with no ambiguity — a check precise enough to reach silver-medal performance at the 2024 International Mathematical Olympiad ("Olympiad-level formal mathematical reasoning with reinforcement learning", Nature, 2025). Training a model this way — rewarding it only when an automatic check passes, with no human or reward model in the loop — is called Reinforcement Learning with Verifiable Rewards (RLVR), and it is the training approach behind DeepSeek-R1, OpenAI's o-series, and most current reasoning models.

A verifier does not have to check a single number. Any output with a precise, checkable specification qualifies, including outputs with no notion of a "reference answer" at all. Consider a floor plan: two rooms may not occupy the same physical space, and every room needs a door. Neither is a matter of opinion, so neither needs a metric or a model — a geometric computation settles both directly. The code below is available in full on GitHub at 05b_floorplan_verifier.py.

rooms_overlap flags rooms only if they overlap on both axes, so two rooms that merely touch along a shared wall are not treated as a conflict; shares_wall then confirms a proposed door actually sits on an edge the two rooms share, instead of trusting the input blindly. Running the verifier against a valid floor plan, one with two overlapping rooms, and one where a room has no door produced this:

--- valid layout: PASS ---

--- overlapping rooms: FAIL ---
  rooms overlap: 'bedroom' and 'bathroom'

--- room with no door: FAIL ---
  room has no door: 'bathroom'

Both failures are the kind of mistake a fluent-sounding description could easily hide: a paragraph describing "a cozy bedroom next to the bathroom" says nothing about whether their rectangles actually overlap by a foot, or whether the bathroom got a door in the final layout. The geometric check catches both without needing to understand the description at all, only the coordinates — the same principle as the math verifier above, applied to a domain with no number to check.

The boundary is exactly what those two demos show: a verifier only exists where a specification is precise enough to check by computer. Math has a numeric ground truth; code has unit tests or a compiler; a formal proof has a proof checker; a floor plan has geometry. Open-ended writing, or "is this a good summary," usually has no such program. That is why BLEU-style metrics, LLM-as-judge, and human preference (LMArena) still matter for everything a verifier cannot reach. A verifier is not automatically safe from the same failure Table 2 introduced, either. If the check is not airtight, a model under RL pressure will find and exploit whatever loophole the verifier leaves open. That is Goodhart's Law again, just with a program standing in for the human reader.
